# Operator friction log (story 5.02)

This log records every point where onboarding an external operator got stuck, slowed down, or needed a guess. It feeds
story 5.03's public integration guide. That guide is "only as good as this log". Acceptance criterion AC5 requires every
entry here to be either addressed in the guide or explicitly noted as unresolved.

## Rules

- **Append-only.** Add new rows at the bottom and never delete or reword a past row. When something changes, update only
  that row's `Status`, `5.03 section` and `Fix` cells, and add a dated note under [Status changes](#status-changes).
  The history is part of the evidence.
- **Pseudonymous.** Operators appear as `OP-1`, `OP-2` and so on. Seeded entries use `QA` (the UAT team acting as an
  operator) or `TEAM` (found by the Blocksmiths in code or during the 5.01 run).
- **No names, no contact details.** Record no email addresses, no personal data and no secret keys. A public key or
  agent id may appear only with the operator's consent (see the
  [runbook](onboarding-session-runbook.md#consent)).
- **Only what is evidenced.** Every row cites where it was seen: a session note, a defect id, a file and line, or a live
  read with its date. A suspicion is not a row.
- **Log it live.** During a session the facilitator adds the row as it happens, using the [template](#template).

### Severity

| Severity | Meaning |
|---|---|
| `blocker` | The operator could not continue without help, or the step silently produces a broken result. |
| `slows` | The operator got through, but lost time, guessed, or needed to ask. |
| `cosmetic` | Wrong or confusing text that cost no real time. |

### Status

| Status | Meaning |
|---|---|
| `open` | Seen, and nobody has fixed or documented it yet. |
| `fixed` | A merged and deployed change removed it. The `Fix` column names the change. |
| `documented` | Not fixed, but the 5.03 guide (or the reference agent's README, until 5.03 exists) tells the operator what to do. |
| `unresolved` | Known, and 5.03 must say plainly that it is unresolved. This is how AC5 is met for anything that will not be fixed in the sprint. |

The `Date` of a seeded row is the day its source first recorded it (the commit date of the defect, evidence file or
fix it cites); for a live session it is the session date. The `5.03 section` column names the guide section that must address the entry. Until 5.03 is written, it gives the
proposed section with the prefix `proposed:`.

## Template

Copy this row into the bottom of the [log](#log) during the session, the moment the friction happens:

```
| F-0NN | YYYY-MM-DD | OP-n | wallet / friendbot / register / deploy / bind / readiness / first run / first settlement / dashboard | What the operator did, what they saw (quote the exact message), what they expected. **Source:** session OP-n, YYYY-MM-DD, runbook step N (plus agent id, tx hash or request id if there is one). | blocker / slows / cosmetic | What got them past it, or "none" | open | proposed: *…* | none filed |
```

Guidance for the facilitator:

- **Quote the screen.** Write the error text exactly. "It failed" cannot be addressed by a guide.
- **One row per friction.** If the same thing happens to `OP-2`, add a new row that refers to the first (`same as
  F-012`). The count of repeats is evidence too.
- **Record your own interventions.** If you had to explain something, that is friction, even if the operator finished.
- **No secrets and no personal data.** If a secret key appears on screen, stop, do not record it, and follow the
  runbook's [key-exposure step](onboarding-session-runbook.md#if-a-secret-key-is-exposed).
