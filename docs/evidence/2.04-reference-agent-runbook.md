# 2.04 runbook — reference external agent, end to end on testnet (BLO-21)

The worked example story 2.04 asks for: take an agent nobody on this team owns,
register it, bind an operator-hosted endpoint to it, get a real workflow routed
to it, execute it, and show the owner's wallet balance move on Stellar Expert.

This page is the procedure. It is written to be run by **someone who did not
write it** — every step states the exact command and what a correct answer looks
like, so a reviewer can tell a pass from a shrug.

**Read [Settlement position](#settlement-position) before step 6.** The payout
step does not work the way the story assumed, and the difference changes what
the evidence is allowed to claim.

---

## Preconditions

| # | Precondition | Notes |
|---|--------------|-------|
| P1 | The API base is live and on **testnet** | `curl -s $API/api/stellar/network \| jq .network` must say `testnet`. Flipping it is `docs/testnet-flip-runbook.md`. |
| P2 | An **owner wallet** you control on testnet | Freighter/xBull/Albedo/LOBSTR/Hana, network set to Testnet. This wallet registers the agent, signs the binding challenge, and receives the payout. |
| P3 | An **HTTPS endpoint** that answers the dispatch contract | ADR `docs/decisions/0001-external-agent-execution.md` defines the request/response; `0004` defines the hardening rules the URL must satisfy (public host, HTTPS, no private ranges). |
| P4 | A **payer wallet** on testnet | Only needed for the x402 pre-authorization in step 6. May be the same person, but a second wallet makes the trail readable. |
| P5 | The backend's `STELLAR_SIGNING_KEY` is a **funded testnet key** | It is the settler. It signs the settlement calls and, per the settlement position below, funds the payout. An unfunded or unset key makes step 7 impossible. |

Throughout: `API=https://orizons.xyz` (or your own deployment). Nothing here
touches mainnet.

---

## Steps

### 1. Fund the wallets via friendbot

```bash
curl -s "https://friendbot.stellar.org?addr=<OWNER_G_ADDRESS>" | jq .successful
curl -s "https://friendbot.stellar.org?addr=<PAYER_G_ADDRESS>" | jq .successful
```

Expect `true` from each. Friendbot tops up an account that already exists rather
than failing, so re-running it is safe. Confirm the balances landed:

```bash
curl -s "https://horizon-testnet.stellar.org/accounts/<OWNER_G_ADDRESS>" | jq .balances
```

### 2. Register the agent on-chain

Do this through the public UI at `$API/app/register`, wallet-signed — the same
path story 1.07 used, and the one an outside operator would actually take. The
success card shows the tx hash and a Stellar Expert link; keep both.

Rules that bite here: the id is `[A-Za-z0-9_]{1,32}`, and an `agt_`-prefixed id
is **reserved** for the 12 seeded agents. Give the agent at least one skill tag —
the planner routes on skills in step 5.

### 3. Sync the registry

The marketplace lists on-chain agents from a periodic sync. Kick it rather than
waiting:

```bash
curl -s -X POST "$API/api/stellar/agents/sync"          # {"synced": <n>}
curl -s "$API/api/agents" | jq '.[] | select(.id=="<AGENT_ID>")'
```

Expect a listing with `"source": "onchain"` and `"owner": "<OWNER_G_ADDRESS>"`.
`source: "seeded"` means you are looking at a catalog agent, not yours.

### 4. Bind the operator endpoint

The browser flow at `$API/app/bind` does all three calls below in one page and
handles the wallet signature; use it unless you are scripting. The API path:

```bash
# preflight — is this URL acceptable at all? (pure, no DNS, no outbound call)
curl -s "$API/api/agents/bind/endpoint-check?url=<ENDPOINT_URL>"     # {"allowed":true}

# mint the challenge
curl -s -X POST "$API/api/agents/<AGENT_ID>/bind/challenge" \
  -H 'content-type: application/json' \
  -d '{"endpoint_url":"<ENDPOINT_URL>"}'
# → {"agent_id","nonce","message","expires_at","ttl_seconds"}

# sign `message` VERBATIM with the OWNER wallet (ed25519 → base64), then:
curl -s -X POST "$API/api/agents/<AGENT_ID>/bind" \
  -H 'content-type: application/json' \
  -d '{"endpoint_url":"<ENDPOINT_URL>","signature":"<BASE64_SIGNATURE>"}'

curl -s "$API/api/agents/<AGENT_ID>/binding"
```

The signature is the whole credential — there is no API key on this route. The
signing wallet must be the one `AgentRegistry.owner_of(<AGENT_ID>)` returns, or
the bind is refused. The challenge expires (`ttl_seconds`); a stale one is a
refusal, not a retry.

`GET .../binding` returns the host only to an anonymous caller and the full URL
to a caller holding the operator key. Either answer proves the binding exists.

### 5. Route a workflow to it

```bash
curl -s -X POST "$API/api/orchestrator/decompose" \
  -H 'content-type: application/json' \
  -d '{"intent":"<INTENT>"}' | jq '{plan_id, steps: [.steps[].agent_id]}'
```

Expect `<AGENT_ID>` among the returned steps. Two traps if it is missing:

- **An unbound agent is not routable.** The planner filters on
  `is_dispatchable` — an on-chain agent with no binding has nothing to execute
  with, so it never enters the candidate list. Step 4 must have succeeded.
- **Demo-kit intents bypass the planner.** An intent containing `calculator`,
  `tetris`, `snake`, `pomodoro` (and their aliases) matches a curated demo kit
  and routes a fixed 6-step pipeline of seeded `agt_` agents. Pick an intent
  that matches your agent's **skills** and none of those words.

Keep the `plan_id`.

### 6. Execute the plan

The payer pre-authorizes, then the plan runs:

```bash
# build the x402 pre-authorization (unsigned XDR, source = the payer)
curl -s -X POST "$API/api/stellar/build/authorize" \
  -H 'content-type: application/json' \
  -d '{"payer":"<PAYER_G_ADDRESS>","agent_id":"<AGENT_ID>","max_amount_usdc":0.2,"ttl_seconds":600}'
# → {"xdr","expires_at"} — sign the xdr in the payer's wallet, then:

curl -s -X POST "$API/api/stellar/submit" \
  -H 'content-type: application/json' -d '{"signed_xdr":"<SIGNED_XDR>"}'
# → {"hash","status":"SUCCESS","return_value":"<32 hex>"}
#   `return_value` IS the auth_id — pass it as auth_id_hex below.

curl -s -X POST "$API/api/orchestrator/execute" \
  -H 'content-type: application/json' \
  -d '{"plan_id":"<PLAN_ID>","auth_id_hex":"<AUTH_ID_HEX>","payer":"<PAYER_G_ADDRESS>"}'
# → {"task_id","read_token"}

curl -s "$API/api/tasks/<TASK_ID>" | jq '{status, spent, charge_tx, proof_tx}'
curl -s "$API/api/trace/<TASK_ID>" | jq '.[] | select(.level=="error")'
curl -s "$API/api/tasks/<TASK_ID>/artifact" | jq '{charge_tx, proof_tx}'
```

If the deployment runs with `TASK_AUTH_REQUIRED` on, the three task reads need
the `read_token` from the execute response: send it as `X-Task-Token: <token>`
(or `?token=<token>` on the trace stream). Without it they answer `404`, which
is deliberate — a wrong token has to look like a missing task.

**What to expect, and it is not what the story assumed.** The dispatch half
works: the step is sent to your bound endpoint, the endpoint's output comes back
as the task artifact. The settlement half does not: `charge_tx` comes back
**`null`** and the task trace carries an `error` line reading
`on-chain settlement failed`, with `PaymentEscrow.charge` failing on
`Error(Auth, InvalidAction)` in the backend log. Nothing was charged and nothing
was paid out. That is the deployed contract's behaviour, not a misconfiguration
on your side — see [Settlement position](#settlement-position), then step 7.

### 7. Produce the payout, and verify it

Per the settlement position, the payout is a **settler-funded SAC transfer** to
the owner — the mechanism story 4.01 proved on testnet:

```bash
.venv/bin/python scripts/prototype_refund.py --buyer <OWNER_G_ADDRESS> --amount 0.05
# → prints status, the tx hash, and the Stellar Expert link
```

`prototype_refund.py` is 4.01's script and its output says "refund" and "USDC";
what it does is `transfer(settler → <address>)` over the configured asset SAC,
which is exactly the payout mechanism, and on testnet the asset is XLM (see the
[honest note on the testnet asset](#honest-note-on-the-testnet-asset)). Reusing
it is deliberate — it is the only value-movement path in this repo that has ever
demonstrably worked, and it is unit-tested in `tests/test_refund_svc.py`.

Then verify the whole claim from the ledger rather than from that output:

```bash
.venv/bin/python scripts/verify_external_settlement.py \
  --agent <AGENT_ID> \
  --owner <OWNER_G_ADDRESS> \
  --tx <SETTLEMENT_TX_HASH> \
  --api-base "$API" \
  --amount 0.05
```

It re-reads `owner_of` live from `AgentRegistry`, confirms the binding, finds
the credit to the owner in Horizon's own record of the transaction, prints the
asset the ledger says moved and names who funded it. Non-zero exit on any
failure, so it can gate a reviewer's spot-check.
